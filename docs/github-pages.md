# Автономная демонстрация на GitHub Pages

GitHub Pages — статический хостинг: [Python/backend не запускается](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site). Поэтому подготовлена отдельная сборка того же интерфейса с браузерным адаптером каталога. Серверная версия FastAPI сохранена.

## Что доступно

Поиск/фильтры/сортировка, таблица и плитки, сравнение, индекс данных, избранное/заметки/история, ручное добавление и редактирование с историей источников, дедупликация, калькулятор, выгрузки CSV и XLSX. Демо содержит 12 явно вымышленных компаний. Локальный каталог изначально пуст.

Все изменения каталога сохраняются в localStorage (`fsup.standalone.catalog.v1`), отдельно от личных данных (`postavka.personal.v1`) и настроек (`postavka.workspace.v2`). Каталог ограничен 1000 записями и фактической квотой хранилища браузера. При отказе сохранения UI показывает ошибку и не заявляет об успехе. Общего каталога между устройствами/посетителями нет. В приватном режиме данные могут исчезнуть после закрытия окна. Очистка данных сайта удаляет всё локальное содержимое.

Табличный экспорт помогает сохранить сведения, но не заменяет резервную копию для автоматического восстановления истории и настроек. Внешний поиск и ИИ не подключены. Сетевые обращения к API в этой сборке не требуются. Платные услуги и OpenRouter не используются. Доступность самого GitHub Pages из нужной сети проверяется после публикации.

## Запуск перед публикацией

Python и БД для этой сборки не нужны. Node.js 22.12+; проверено на Node 24:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd test
npm.cmd run build:pages
npm.cmd run preview -- --mode pages --port 4173
```

Открыть **http://127.0.0.1:4173/Food-Supplier-Finder/**. Результат: `frontend/dist-pages`. Обычный `npm run build` по-прежнему создаёт серверный frontend в `frontend/dist`.

Для браузерной проверки (в другом окне PowerShell; Playwright Chromium устанавливается отдельно):

```powershell
Set-Location frontend
npx.cmd playwright install chromium
$env:PLAYWRIGHT_STANDALONE = '1'
npm.cmd run test:e2e -- --output test-results-pages
```

Конфигурация сама поднимает локальный preview, если он ещё не запущен. Сценарий ошибки backend пропускается именно для статического режима: backend здесь отсутствует. Проверяются реальные операции в браузере, включая перезагрузку, историю правок, отказ хранилища и отсутствие обращений к `/api`.

## Публикация из ветки gh-pages

`main` хранит исходники и полную документацию, `gh-pages` — готовую статическую версию. Истории веток отдельные: в ветке показа нет Python-кода, ТЗ, пользовательской БД или секретов. В неё входят `index.html`, `assets/`, `.nojekyll`, краткий `README.md` и `deployment.json` с исходным коммитом.

В GitHub → Settings → Pages выбрать **Deploy from a branch**, ветку **gh-pages**, каталог **/ (root)**. Публичный адрес: `https://themickart.github.io/Food-Supplier-Finder/`. После первого включения дождаться успешной сборки GitHub Pages и проверить URL из нужной сети.

Обновление после изменения исходников:

```powershell
# Из корня; до этого установить frontend-зависимости через npm ci.
git add .
node scripts/check-publication.mjs
git commit -m "Describe the source changes"
git push origin main
node scripts/publish-pages.mjs --push
```

Скрипт выпуска требует чистую `main`, запускает проверку исходников, TypeScript и Vite Pages, проверяет статический артефакт. Через отдельный временный Git-индекс формирует снимок `gh-pages`, сохраняя прежний коммит этой ветки родителем при повторном выпуске. Содержимое основного checkout/индекса не переключается; удалённая история не переписывается. Без `--push` создаётся только локальный коммит сборки. Генерируемые README/metadata не содержат пользовательских данных.

Workflow `.github/workflows/pages.yml` — **Check Pages build** — выполняется на push в `main` и вручную. Он проверяет состав репозитория, модульные и браузерные сценарии, собирает/проверяет артефакт и сохраняет его в Actions. Деплой сайта берётся именно из `gh-pages`; workflow проверки самостоятельно ветку не меняет.

[Состав исключений и проверка публикации](publishing.md). Версии Actions закреплены коммитами из [официального примера Vite](https://vite.dev/guide/static-deploy.html#github-pages). Runtime проекта на сайте остаётся автономным; ни Python, ни серверная БД на Pages не запускаются.

`frontend/.env.pages` содержит только публичные параметры:

| Переменная | Значение | Назначение |
| --- | --- | --- |
| `VITE_RUNTIME_MODE` | `standalone` | Браузерный адаптер вместо `/api/v1` |
| `VITE_BASE_PATH` | `/Food-Supplier-Finder/` | Путь проекта на Pages |

При другом имени репозитория изменить base; для собственного домена/корня — `/`. API-ключи нельзя помещать в `VITE_*`, исходники или Pages.

## Сохранение архитектуры для дальнейшего развития

Основной серверный вариант сохраняет критическую логику и общий каталог на backend, как требует ТЗ. Браузерная реализация — отдельное ограниченное исключение для согласованного бесплатного показа. Интерфейс получает одинаковый контракт через `api.ts`; браузерные модули/фикстуры не входят в обычный серверный bundle.

На Pages нет регистрации, синхронизации и серверной авторизации. Подключать секретный поисковый/ИИ API прямо из браузера нельзя. Для развития нужны server-side адаптер, БД и доступный хостинг; локальные записи переносить отдельным инструментом с проверкой, сохранением ID, источников и дат.

`scripts/build_demo_snapshot.py` обновляет только вымышленную фикстуру из временной БД. Он не читает пользовательскую БД. Даты в снимке не обновляются при загрузке страницы; правило 90 дней применяется к сохранённым датам. Скрипт запускать осознанно при изменении демонабора; генерация не нужна для каждой Pages-сборки.
