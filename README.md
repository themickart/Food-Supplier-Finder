# FSUP · FOOD SUPPLIER WORKSPACE

Рабочее пространство закупщика food-бизнеса: поиск по каталогу поставщиков, фильтры, сравнение, заметки, оценка доступности сведений и экспорт. Проект подготовлен как тестовое задание с возможностью дальнейшего развития в серверный продукт.

**[Открыть демонстрацию](https://themickart.github.io/Food-Supplier-Finder/)** · [Ветка собранного сайта](https://github.com/themickart/Food-Supplier-Finder/tree/gh-pages) · [Отчёт о проверках](docs/test-report.md)

При первом открытии нажмите **«Деморежим»**. В нём 12 явно вымышленных компаний; реальный/локальный каталог изначально пуст. Доступность публичного URL зависит от включения Pages для ветки `gh-pages`, каталог `/`.

**Статус — функциональный прототип.** Реальный внешний поиск не подключён, автоматический сбор новых компаний не выполняется. ИИ отложен; OpenRouter и другие платные API не вызываются. Поиск работает по имеющимся записям. Демоданные никогда не выдаются за найденные реальные компании.

## Что находится в ветках

| Ветка | Содержимое | Для чего нужна |
| --- | --- | --- |
| `main` | React/TypeScript frontend, FastAPI backend, миграции, тесты, Docker и документация | Разработка, локальный сервер, дальнейшее развитие |
| `gh-pages` | `index.html`, собранные JS/CSS в `assets/`, `.nojekyll`, краткий README и `deployment.json` | Показ тестового задания на GitHub Pages |

Ветка `gh-pages` создаётся отдельной историей и содержит только статическую сборку. В `deployment.json` указан исходный коммит `main`. ТЗ, его внутренняя сверка, реальные локальные БД, ключи, выгрузки, зависимости, скриншоты и логи исключены из публикации.

## Как показать задание за 5–7 минут

1. Откройте демонстрацию и переключитесь в **«Деморежим»**. Покажите маркировку вымышленных данных и пустой отдельный локальный каталог.
2. Найдите **«Моцарелла»**, выберите **Екатеринбург**: останутся две компании. Сбросьте условия, попробуйте быстрые/расширенные фильтры и сохраните набор поиска.
3. Переключите плитки на таблицу. Выберите компании флажками и прокрутите страницу: панель массовых действий остаётся сверху. Настройте столбцы и плотность.
4. Нажмите на **индекс данных**: откроются семь критериев. Это оценка наличия и актуальности сведений, а не рейтинг надёжности компании.
5. Откройте **«Сырная мастерская» → «Условия и доставка»**. В калькуляторе укажите 5 кг: при учебной цене 590 ₽/кг получится 2 950 ₽ и предупреждение о минимуме 10 кг. Проверьте явную кратность закупки.
6. Добавьте компании в сравнение: доступны до пяти поставщиков. Товары, валюта, единицы и фасовка видны; автоматического победителя нет.
7. Сохраните компанию в избранное, напишите заметку, перезагрузите страницу и снова откройте деморежим: личные данные сохраняются в браузере.
8. Выберите компании либо отфильтрованную выдачу и выгрузите **CSV и XLSX**. Заметки включаются отдельно; ссылки на источники и даты входят в отчёт.
9. В локальном каталоге добавьте собственную реальную компанию со ссылкой на источник. Измените адрес/документы, откройте историю источников. Повторное добавление известного домена обрабатывается как дубликат.
10. На страницах **«Возможности проекта»** и **«Источники и интеграции»** покажите реализованные функции и ограничения. В карточке можно скопировать контакты и шаблон запроса КП; сервис не отправляет письма.

## Реализованные функции

- Поиск по названию, товару, категории, расположению и географии доставки; нормализация регистра и `ё`, объяснение совпадения по сохранённым полям.
- Три начальные категории: молочная продукция, замороженные продукты, упаковка. Три контрольных рынка: Екатеринбург, Казань, Москва. Реальные записи могут дополнять регионы.
- Фильтры категории/региона/доставки, наличия сайта, контактов, минимального заказа, документов и условий; отдельный фильтр проверенных по источнику контактов, статус актуальности и индекс данных.
- Диапазоны цены и заказа с обязательными единицами. Цена привязана к конкретной товарной позиции и валюте; цена за упаковку автоматически не превращается в цену за кг.
- Сортировка, пагинация, сохранённые наборы условий, активные фильтры и сброс. Плитки по умолчанию, таблица, настройка столбцов/плотности, контекстные и массовые действия.
- Подробная карточка: ассортимент, контакты, адрес отдельно от географии доставки, условия, документы-ссылки, источники/даты, противоречия и заметки.
- Ручное добавление и редактирование, валидация ИНН, нормализация, консервативная дедупликация: ИНН → домен → название и адрес. При неоднозначности автоматического слияния нет.
- Сохранение нескольких источников и прежних значений при правках. Новые ручные факты автоматически не подтверждаются. Данные старше 90 дней требуют перепроверки.
- Сравнение до пяти компаний, избранное, создание/изменение/удаление заметок и история последних десяти поисков.
- Калькулятор одной позиции: количество × цена, введённая пользователем кратность и сопоставимый минимум. Вес упаковки, доставка, скидки, налоги и сборы не угадываются.
- Экспорт выбранных записей или всей отфильтрованной выдачи в CSV UTF-8 с BOM и XLSX. Корректное экранирование, защита от формул, источники/даты, заметки по выбору.
- Адаптивность, состояния загрузки, ошибок, пустой выдачи и отказа хранилища. Копирование контактов и запроса коммерческого предложения.

Пробный бренд FSUP использует кастрюлю с поварёшкой. Прежний бренд сохранён до отдельного утверждения: **«О сервисе» → «Вернуть „Поставку“»**.

## Два режима: что работает и где хранятся данные

| Возможность | GitHub Pages / standalone | Серверный запуск |
| --- | --- | --- |
| Интерфейс, фильтры, сравнение, калькулятор | В браузере | В браузере, данные через API |
| Каталог и правки | localStorage текущего браузера | Серверная БД |
| Избранное, заметки, история, настройки | localStorage | localStorage |
| CSV/XLSX | Генерация на устройстве | Генерация на backend; заметки передаются только по выбору |
| Python/PostgreSQL | Не запускаются | FastAPI + SQLite; PostgreSQL подготовлен |
| Внешний поиск / ИИ | Не подключены | Не подключены |
| Общий каталог между устройствами | Нет | Есть в пределах одной серверной установки |

В Pages нет сервера приложения, регистрации, ролей и синхронизации. Каталог ограничен 1000 записями и квотой браузера. Очистка данных сайта/приватного сеанса может удалить записи. Один профиль браузера доступен всем, кто им пользуется. CSV/XLSX — табличные отчёты, а не полная резервная копия для автоматического восстановления истории и настроек.

Ключи localStorage: `fsup.standalone.catalog.v1` — автономный каталог, `postavka.personal.v1` — личные данные, `postavka.workspace.v2` — настройки/наборы фильтров. Эти данные не включаются в сборку и не отправляются на GitHub как пользовательский каталог.

## Технологии и устройство проекта

Frontend: **React 19 + TypeScript + Vite**, собственные CSS-компоненты и Lucide. Backend: **Python 3.11+ + FastAPI + SQLAlchemy + Alembic**. SQLite для простого запуска; PostgreSQL 16/Docker Compose подготовлены. Pytest, Vitest и Playwright для проверок.

```text
frontend/src/
  api.ts                 выбор серверного / браузерного адаптера
  components/            каталог, карточки, фильтры, сравнение и формы
  standalone/            браузерный каталог, изменения, экспорт и учебный снимок
  calculator.ts          расчёт конкретной позиции
backend/app/
  main.py                API, миграции, ошибки, раздача frontend
  catalog.py             поиск, дедупликация, импорт и правки
  schemas.py             валидация
  scoring.py             объяснимый индекс сведений
  providers.py           контракт внешнего источника; сейчас not_configured
  exporter.py            CSV / XLSX
backend/migrations/      схема БД и обновления индексов
backend/tests/           API, данные, экспорт, оценка, миграции
frontend/e2e/            пользовательские сценарии desktop / mobile
scripts/                 запуск, резервирование, исправление, проверки, выпуск Pages
docs/                    архитектура, источники, ограничения и эксплуатация
```

Основной продукт — модульный монолит. Серверная сборка сохраняет критическую логику и общий каталог на backend. Отдельный браузерный адаптер позволяет показать интерфейс на статическом хостинге без сервера. При обычной сборке он не входит в серверный bundle. [Подробнее об архитектуре](docs/architecture.md).

## Быстрый локальный запуск версии Pages

Нужны Node.js 22.12+ и npm; проверено на Node 24. Python и БД не нужны.

```powershell
git clone https://github.com/themickart/Food-Supplier-Finder.git
Set-Location Food-Supplier-Finder/frontend
npm.cmd ci
npm.cmd run build:pages
npm.cmd run preview -- --mode pages --port 4173
```

Открыть **http://127.0.0.1:4173/Food-Supplier-Finder/**. В Linux/macOS команды те же: `cd` вместо `Set-Location`, `npm` вместо `npm.cmd`.

Результат — `frontend/dist-pages`. Публичные настройки в `frontend/.env.pages`: `VITE_RUNTIME_MODE=standalone`, `VITE_BASE_PATH=/Food-Supplier-Finder/`. При другом имени репозитория меняется base path, для собственного домена/корня используется `/`. Секреты в `VITE_*` не помещать.

## Серверный запуск без Docker

Из корня на Windows, Python 3.11+ и Node.js 22.12+:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
Set-Location frontend
npm.cmd ci
npm.cmd run build
Set-Location ..
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Открыть **http://127.0.0.1:8000**, документация API — **http://127.0.0.1:8000/docs**. При старте выполняются миграции и создаются только учебные записи. Реальный каталог пуст, файл БД — `data/catalog.db`; повторный запуск его не сбрасывает. Альтернатива команде Uvicorn: `scripts/start.ps1`.

Linux/macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.lock.txt
cd frontend && npm ci && npm run build
cd ..
.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Для разработки frontend можно запускать `npm run dev` при работающем backend на 8000: Vite проксирует `/api`. Для показа собранной серверной версии используйте `npm run build` и Uvicorn.

## Конфигурация и Docker

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | `sqlite:///./data/catalog.db` | SQLAlchemy URL, для PostgreSQL `postgresql+psycopg://…` |
| `SEED_DEMO` | `true` | Создание учебных записей; отключение не удаляет существующие |
| `STALE_DAYS` | `90` | Порог необходимости перепроверки |
| `POSTGRES_PASSWORD` | `local-demo-only` | Только Compose; заменить при серверном размещении |

Сервер читает переменные процесса. `.env` автоматически использует **Docker Compose**, обычный Python-запуск его не загружает. Для него задайте `$env:ИМЯ` / `export ИМЯ` до старта. Для существующей БД смена `STALE_DAYS` не изменяет даты источников.

```powershell
Copy-Item .env.example .env
docker compose up --build -d
```

Compose подготавливает PostgreSQL 16 в постоянном volume, приложение на loopback 8000; БД наружу не публикуется. Пароль в connection URL должен быть URL-безопасным или URL-кодированным. **Runtime Docker/PostgreSQL в текущем окружении не проверен**, проверка конфигурации не равна проверке работающего контейнера. Проверенный серверный вариант — SQLite.

Резервирование и восстановление БД, исправления оператором: [docs/deployment.md](docs/deployment.md). Публичный сервер с правами редакторов требует отдельной авторизации; локальный API не предназначен для свободной записи всеми посетителями.

## Проверки

Проверенный набор: **39 Pytest, 24 Vitest, 22 серверных E2E и 24 автономных E2E**. В E2E используются desktop Chromium и мобильный viewport iPhone 13 в Chromium, не Safari. Есть проверки единиц/валюты/минимума, дубликатов, истории, источников, экспорта, формул, пустой выдачи, ошибок сети и localStorage, прокрутки и закрепления панели.

```powershell
# Из корня
.\.venv\Scripts\python.exe -m pytest -c backend/pyproject.toml -q
.\.venv\Scripts\python.exe -m ruff check backend
node scripts/check-publication.mjs
Set-Location frontend
npm.cmd test
npm.cmd run build:pages
npm.cmd run check:publication -- --pages-dir frontend/dist-pages
npx.cmd playwright install chromium
$env:PLAYWRIGHT_STANDALONE = '1'
npm.cmd run test:e2e -- --output test-results-pages
```

Playwright сам поднимает preview, если он ещё не запущен. В окружении с локальной папкой браузеров задайте `PLAYWRIGHT_BROWSERS_PATH` одинаково для установки и запуска. Для серверных E2E используйте **отдельную тестовую БД**, иначе тесты добавят записи в ваш каталог. Пример двух терминалов и результаты — [в отчёте](docs/test-report.md).

Синтетический серверный поиск на 10 000 компаниях: медиана 236 мс, максимум 268 мс, 10 последовательных запусков одного процесса без HTTP/браузера. Это измерение текущего компьютера, не гарантия нагрузки на хостинге. Бенчмарк: `scripts/benchmark_catalog.py`.

## Как обновлять GitHub Pages

Из чистой `main` после сохранения исходных изменений в коммит:

```powershell
git push origin main
node scripts/publish-pages.mjs --push
```

Скрипт проверяет исходники, пересобирает Pages, проверяет артефакт, формирует отдельный Git-индекс и коммит `gh-pages`, затем выполняет обычный push без переписывания удалённой истории. Основной checkout и индекс `main` не переключаются. Без `--push` создаётся только локальный коммит сборки. Предварительно нужны `npm ci` в frontend и настроенная Git-авторизация.

GitHub → **Settings → Pages → Deploy from a branch → gh-pages → / (root)**. `.nojekyll` хранится в ветке сборки. Workflow **Check Pages build** проверяет `main` при push или ручном запуске и сохраняет статический артефакт; публикация сайта берётся из `gh-pages`.

[Подробности Pages](docs/github-pages.md) · [Что исключено из Git и как проверить публикацию](docs/publishing.md).

## Что пока не реализовано

- **Реальный внешний поиск и автоматическое сохранение его результатов.** Ручное добавление — вспомогательный путь, оно не закрывает этот критерий исходного MVP. Поисковый API не имитируется.
- **ИИ-интерпретация свободного запроса**, синонимы и модельное ранжирование. Обычный поиск от ИИ не зависит.
- **Автоматическая проверка контактов, документов и работы компании.** Наличие сайта/источника не означает готовность отгрузить. Неизвестное остаётся «Не указано».
- **Серверная общая БД на Pages**, авторизация, организации, роли и синхронизация браузерных данных.
- **Автоматическое расписание обновлений**, CRM, отправка писем и аналитика закупок.
- Полевые проверки PostgreSQL/Docker/VPS и доступности каждого будущего API из целевой инфраструктуры.

Бесплатный Overpass пробно вернул реальные объекты, но затем повторные запросы завершились тайм-аутами; стабильность, CORS и достаточное покрытие food-категорий не подтверждены. Он не включён как работающий источник. [Отчёт по кандидатам и реальным пробам](docs/data-sources.md).

## Как развивать проект дальше

| Этап | Как реализовать | Как проверить результат |
| --- | --- | --- |
| Внешний поиск | Выбрать допустимый источник, проверить лицензию/хранение, доступность, ключ и квоту; реализовать контракт `providers.py`. Временные кандидаты → нормализация → дедупликация → каталог, с источником и датами | Контрольные запросы по категориям/регионам, доля релевантных/сохранённых/дубликатов; тайм-ауты, лимиты и частичные отказы |
| Обогащение сайтов | Отдельный разрешённый сетевой модуль: проверка DNS/IP и каждого редиректа, запрет внутренних адресов, ограничение размера/времени, соблюдение правил источника | Неполные/невалидные ответы, SSRF, ошибка источника; факты сохраняются только с происхождением |
| ИИ | Подключаемый серверный парсер запроса → валидируемая схема фильтров. Конфигурируемый провайдер, жёсткий лимит расходов, отключение/fallback | Ошибка модели не ломает обычный поиск; компании, контакты и цены не генерируются |
| Общая БД | Развернуть серверный режим на доступном хостинге; протестировать PostgreSQL/миграции/backup. Перенос из браузера — отдельный валидируемый импорт с сохранением ID и истории | Два устройства видят общий каталог, восстановление копии реально проверено |
| Масштабирование | Нормализовать товары/факты/источники, PostgreSQL FTS/индексы, кеш, фоновые задания со статусами и квотами | Реальные объёмы и параллельная нагрузка, повторные запросы, отказ одного источника |
| Публичный SaaS | Серверные аккаунты, организации/роли, права оператора на исправления, изоляция заметок, журнал действий | Проверка доступа между пользователями и организациями; чужие личные данные недоступны |
| Проверки поставщиков | Отдельные адаптеры реестров/платных проверок, типизированные проверенные факты и даты | Каждый статус соответствует конкретному факту/источнику; рейтинг надёжности не выводится из одного наличия сайта |

Начинать развитие стоит с настоящего допустимого поискового источника и серверной эксплуатации, затем подключать ИИ и платные проверки по согласованным лимитам. Микросервисы на этом этапе не нужны.
